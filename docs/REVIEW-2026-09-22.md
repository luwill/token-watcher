# Token Watcher 产品与代码评审

评审日期：2026-09-22。版本：1.7.0，HEAD `e183a40`，包含工作区已有的 `web/app.js` 修改。此次未修改业务实现，未访问真实用量库或调用真实厂商凭证。

**结论：功能覆盖已经较完整，但数据可信度与跨模块契约仍存在发布前应修复的问题。** 多源采集、增量游标、配额、余额、费用、会话钻取、ROI、导出和菜单栏组成了完整的个人工具。继续扩源的收益，暂时低于修复重复统计、范围截断、告警失效和错误状态误导。

## 产品功能评审

值得保留的设计：

- 本地事件归一化与多工具汇总能解决使用者在不同工具之间切换、无法集中查看用量的问题。
- token、积分、配额和余额分别建模；Antigravity 标注估算、Qoder 不强行兑换 token，方向正确。
- UI 之外还有 CLI、CSV、后台服务与菜单栏入口，兼顾日常查看和脚本使用。
- 有离线模式、回环地址绑定、Host 检查，以及数据库备份，具备长期本地运行的基础。

主要产品缺口：

| 优先次序 | 问题 | 建议闭环 |
|---|---|---|
| 1 | “全部”不能真正查全部；归档会把历史统计变大 | 先修下述 F1/F2，用跨路径重放与历史日期验收 |
| 2 | 原始 token、API 等值、订阅实付、积分的可比性有限；ROI 缺价格仍给零值 | 在费用/ROI 中显示价格覆盖率、未配价用量和估算来源；完整度不足时禁用价值判断 |
| 3 | 错误、未安装、未使用、缺凭证、接口失效没有统一状态语义 | 每源展示最后成功时间、失败原因、数据完整度及可执行的处理办法；接入 Cursor poller 的 status |
| 4 | 配置需手填文件，Claude/Codex 数据路径写死 | 增加路径和启停配置入口，尊重自定义目录；订阅金额支持校验、保存与反馈 |
| 5 | 范围选择的影响不直观 | 明确每块的时间范围：工具调用固定 30 天，ROI 为本月，费用摘要为今日/7天/累计；支持统一范围和自定义日期 |
| 6 | 项目成本与配置操作未闭环 | 增加项目筛选/成本视图，但先保存项目完整身份，避免同名目录合并；未配价模型提供配置入口 |

ROI 当前以自然月用量对比整月价格。用于展示“本月 API 等值/订阅费”可以，但 `×N 划算` 容易被理解为续订结论；月中、价格缺失、导入历史不完整、订阅账期不同都影响该判断。建议先使用中性比值，并披露数据覆盖范围。

README 也需要同步：Roadmap 仍列已落地的 ROI/Cursor/英文 README；出站请求段落写“四类”，表格实际六行，离线说明又写“三类”。这些属于文档漂移，不是新的运行时缺陷。

## 已确认代码问题

### F1 · P1：Codex 归档或搬移日志会重复累计

位置：`src/collectors/codex.js:97`，工具调用键同样见第 50 行。

事件键包含绝对 `path`。扫描器同时采集 sessions 和 archived_sessions；文件搬移后新路径无游标，会从头读取，而旧 events 被保留。路径变化使同一用量获得新键，历史 token、费用和工具调用都会重复。

复现：相同两条累计记录（0 → 100）以两个路径采集到同一隔离 Store，结果为 `n=2, total=200`，预期只有 `total=100`。

建议：基于稳定会话身份与稳定事件身份去重，文件位置仅用于追踪游标。既有库需要明确迁移策略，单纯改新键或升 collector version 会再次重复；历史修复应独立备份并验收。

### F2 · P1：“全部”被解析成 30 天，CSV 静默漏历史

位置：`src/server.js:351` 和 `src/server.js:399`。

前端用 `days=0` 表示全部，后端 `Number(...) || 30` 将合法的 0 当作缺省值。图表与排名只统计近 30 天，累计卡仍是全量，导出的 CSV 同样漏掉 30 天前数据。

复现：插入近期 200 和 100 天前 500 tokens；请求 `/api/summary?days=0` 得到 `range_days=30`、累计 700、范围合计 200；`export.csv?days=0` 只有近期行。

建议：分别判断参数缺失、非法数字与合法零值；summary/export 共用参数解析，增加超过 30/90 天的接口测试。

### F3 · P1：菜单栏仍消费旧配额格式，Codex 显示与告警失效

位置：`menubar/main.swift:22`、第 65 行；生产者为 `src/codexQuota.js:28` 及 `codexQuotaView()`。

后端输出 `{plan_type, windows:[{used_percent, window_minutes, resets_at}]}`，且会把旧形状也转成 windows。Swift 的 `DataQ` 仍只有平铺的 `used_percent`。它是 optional，解码不会报错，却始终得到 nil，导致菜单栏的 Codex 百分比与 80%/95% 通知分支不执行。

验证方式：生产者/消费者结构静态核对，未编译或启动原生 App，未实际触发通知。

建议：Swift 解码 windows，按时长区分 5 小时/周窗口，分别显示和告警；用真实后端 JSON 形状做 Swift 解码契约测试，并规定过期快照的处理方式。

### F4 · P1：逐行解析回调异常逃逸，扫描事务无法可靠回滚

位置：`src/collectors/lines.js:14-20`。

`onLine()` 在 stream 的 data 事件里执行，没有 try/catch。这里的异步回调异常不会自动 reject 外层 Promise，扫描器 `await collector` 的 catch 因而接不到。字段类型异常引起 SQLite 绑定错误等情况可以触发；一次性 CLI 会退出，serve 的全局 uncaughtException 日志兜底也不能保证本文件正常回滚。

复现：在外层 try/await/catch 中调用 readLinesFrom，令 onLine 抛出 Error；子进程退出码为 1，外层 catch 未执行。

建议：捕获回调异常并销毁 stream、reject Promise，让 scanner 的事务回滚和 parse_errors 处理接管。增加“坏记录 → 当前文件回滚 → 下一文件仍可处理”的行为测试。

### F5 · P2：首次采集失败显示 empty，doctor 可误报无问题

位置：`src/server.js:113-114`，消费者为 `src/doctor.js`。

computeHealth 先判断没有历史事件，再判断 parse_errors。新源遇到格式漂移、缺解压程序或 SQL 失败时，恰好还没有历史事件，于是失败被标成 empty。doctor 只把 status=error 计入问题列表，因此这类源可能仍得到成功退出码和“未发现问题”。

复现：空源传入 `{parse_errors:1,last_error:'bad format'}`，结果是 `status:'empty', parse_errors:1`。

建议：失败状态优先于空数据；另区分未安装/无数据/未授权。现有 stale 判定也仍只比较文件 mtime 与事件时间，对纯工具消息追加可能误报，应另设用量候选行或采集水位证据。

### F6 · P2：未配价用量被 ROI 当成零成本

位置：`src/roi.js:53-54`、第 85 行、第 94-98 行。

aggregateCosts 会将缺价模型排除并返回 unpriced；computeRoi 丢弃该信息，缺失的 tool 成本通过 `?? 0` 变成零，最终输出 ratio=0。部分缺价则输出偏低但看似完整的比值。

复现：Codex 有本月用量但模型无价格，月费配置 100；返回 `api_cny:0, paid_cny:100, ratio:0`，没有对应条目的缺价状态。

建议：按工具/模型过滤范围返回已配价与未配价覆盖情况；全缺价返回 null，部分缺价标明仅为已知部分，避免直接给出“划算”等判断。

### F7 · P2：端口重试重复启动轮询、监听器与备份定时器

位置：`src/server.js:293-330`；重试入口在 `bin/tokenwatcher.js` 的 tryListen 循环。

每次 startServer 在 listen 成功之前注册 scanner 监听器、启动各 poller 和备份任务。遇到 EADDRINUSE/EACCES 后只 reject，没有撤销副作用；CLI 随后再次调用 startServer。默认端口被占是功能明确支持的正常场景，会因此留下重复网络轮询、费率计算和后台任务。

复现：同一 scanner/poller 启动一个服务，再向已占用端口尝试一次；第二次虽然失败，四个 poller 的 start 总调用数从 4 增至 8，update 监听器从 2 增至 4。

建议：listen 成功后再启动后台生命周期，或失败时完整清理。测试验收占用端口后找到新端口时，每类任务仍只运行一份。

## 结构与测试

采集器按源隔离、增量游标、版本回填、统一 Store、前端纯函数模块与三平台 CI 是有效基础。项目已具备较有价值的 fixture 测试，不宜因这些边界问题推倒重做。

当前主要维护压力来自 `web/app.js` 896 行、`test/run.mjs` 1737 行，以及 server 同时承担汇总、路由和生命周期。建议随修复拆分 summary、health、HTTP lifecycle 和面板模块；不必引入前端框架或全新构建链。

新增测试应聚焦遗漏的契约：跨路径幂等、`days=0` 的全链路结果、Swift 消费后端 JSON、stream 回调异常传播、首次错误状态、缺价 ROI、端口重试清理。现有 tests 中虽然请求过 `days=0`，断言检查的是始终全量的 costs.by_model，因此没有检验该参数是否真的生效。
